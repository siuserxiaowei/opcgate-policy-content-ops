# 从“写得快”到“写得有依据”：我如何做一个政策内容运营助手

## 一、我没有先问 AI 能做什么，而是先找运营最容易出错的一步

园区和创业服务机构经常需要围绕 AI、智能体、一人公司、算力、办公空间和创业扶持制作内容。表面上这是写作任务，真正消耗时间的却是写作前后的核验：

- 同一个话题与哪些政策真正相关；
- 链接是不是官方原文；
- 数据是哪天记录的；
- 政策描述的是框架、实施细则，还是正在开放的申报；
- 哪句话是已知事实，哪句话只是内容推断；
- AI 有没有把“相关”写成“符合资格”。

通用写作模型可以快速给出一篇流畅文章，但流畅不等于可信。政策内容一旦出现未经证明的金额、资格、截止时间和官方背书，运营反而需要花更多时间返工。

因此，我把作品目标定义为：**不是替运营自动发内容，而是先把证据和边界整理好。**

## 二、产品工作流：先证据，后生成，再人工发布

完整流程如下：

```text
公开内容 / 自拟选题
  → 关键词与运营意图
  → 政策、城市和载体数据关联
  → 来源、日期、匹配理由和适用边界
  → 事实 / 推断 / 待核验草稿
  → ModelScope API-Inference 受限改写（可选）
  → 确定性规则后扫
  → 人工核验清单
  → 手动发布
```

这里有三个重要选择。

第一，**相关性不是资格判断**。系统可以告诉运营某个话题与哪条政策在关键词和场景上重合，但不能替主管部门判断主体是否符合条件。

第二，**模型不是唯一运行路径**。规则分析、证据卡片和基础草稿不依赖模型 Token；模型额度不足、接口异常或输出未通过扫描时，应用会降级到确定性草稿。这能保证评委打开 Demo 时仍然完成核心流程。

第三，**发布门禁不替代人工核验**。界面中的清单用于把必要动作显式化，不能证明事实已经自动核实，也不能防止开发者工具绕过。真正的事实核验仍由发布者完成。

## 三、为什么选择 ModelScope API-Inference

ModelScope API-Inference 提供 OpenAI API 兼容接口，适合把开源模型接入已有应用。比赛版使用环境变量保存 Access Token，浏览器和仓库中都不出现密钥。

模型收到的不是整套数据库，而是规则引擎筛出的最小证据上下文，包括政策名称、城市、摘要、来源、数据日期和边界。提示词明确禁止补充金额、资格、排名、热度、用户量和官方背书。

模型返回后还会检查：

- 是否保留“事实 / 推断 / 待核验”结构；
- 是否明确“政策关联不等于资格判断”；
- 是否声明不自动发布、需要人工核验；
- 是否出现保证获批、可领取、补贴到账等高风险表达；
- 是否出现证据上下文中不存在的数字断言。

不通过就自动弃用模型结果，而不是为了展示 AI 强行采用。

## 四、数据与可解释性

作品复用 OPC Gate 的公开数据快照：125 条政策、42 个城市 / 适用范围和 128 个社区 / 载体样本。数据快照日期为 2026-05-22，不把开发时间、页面更新时间和政策状态混成一个口径。

每条匹配结果都会展示：

- 命中的关键词；
- 相关性和综合置信度；
- 来源类型与原文链接；
- 数据记录日期；
- 适用边界。

分数只是内容研究排序，不是政府评分、资格概率或商业推荐。

## 五、活动期内原创部分与既有基础

OPC Gate 的政策导航和数据底座早于本次活动存在，所以我没有把整个老项目包装成今天从零完成。

活动期内，`opc-vibesocial-trust-agent` 于 2026-07-23 创建为独立的社交内容可信核验原型，并于 7 月 24 日公开发布。本届比赛版在该原创衍生能力上继续开发，新增了：

- 面向政策内容运营的产品定位；
- ModelScope Gradio 创空间版本；
- API-Inference 适配和无 Token 降级；
- 三层草稿工作流；
- 模型输出后二次扫描；
- 本届比赛专用测试、演示和提交资料。

Git 历史完整保留，不重写旧提交时间。

## 六、测试与验收

我没有只测试“按钮能不能点”，而是把产品边界写进回归测试：

- 完整数据范围是否为 125 / 42 / 128；
- 生成草稿是否包含三层结构和人工核验要求；
- 是否保留可访问的政策来源；
- 是否拒绝 `javascript:`、本机和私网 URL；
- 是否拦截保证、资格、金额和官方背书；
- ModelScope Token 缺失时是否安全降级；
- 是否保留发布门禁逻辑；
- 页面是否没有上一场比赛标签残留。

自动化测试通过后，还会分别在桌面和手机视口完成完整演示。

## 七、我希望验证什么

当前没有真实用户量和节省时长数据，因此不先给一个漂亮但不可验证的数字。下一步会用真实运营任务记录：

1. 从选题到可核验草稿的完成时间；
2. 需要打开的页面和复制次数；
3. 发布前发现的事实 / 边界问题数量；
4. 草稿返工次数；
5. 运营人员是否能理解每条结果的来源和限制。

这个作品真正想解决的，不是“让 AI 多写一篇”，而是让政策内容运营少做一次危险的猜测。
